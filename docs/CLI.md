## 1. Overview

`mem` is the command-line entry point of ACDM (Agent Cross-Device Memory System). ACDM uses a Git-synchronized, append-only JSONL store to record "which agent changed which files on which device", so that multiple agents on multiple machines share one project memory. `mem` serves manual operation and scripting; `mem-mcp` exposes the same core capabilities as MCP tools (see [MCP.md](MCP.md)). Both read and write **the same store**, and the two can be mixed freely.

### 1.1 Build and installation

Rust stable (edition 2021) is required; only the git operations in `sync` and `resolve` need `git` on the machine.

```bash
# Build the release binaries (the workspace builds both mem and mem-mcp)
cargo build --release
# Artifacts:
#   target/release/mem
#   target/release/mem-mcp
```

Put `target/release/mem` on your `PATH` (or invoke it by absolute path). The examples below assume `mem` is on `PATH`.

### 1.2 Global option and store discovery

All subcommands share one global option:

| Option | Required | Default | Description |
| --- | --- | --- | --- |
| `--path <DIR>` | No | See the discovery rules below | Store root directory; `mem --path <DIR> <subcommand>` and `mem <subcommand> --path <DIR>` are equivalent |

Store discovery priority, highest first (`mem` and `mem-mcp` behave identically; implemented in `mem-core/src/util.rs::resolve_store_root`):

1. explicit `--path <DIR>`;
2. the `ACDM_STORE` environment variable;
3. walk up from the current working directory (CWD) looking for the **nearest** store root: a directory that contains a `.mem` marker file or an `events/` directory;
4. fallback: the CWD itself.

`init` is the only exception: it **does not search upwards** and uses only an explicit `--path` (a subcommand-level `--path` wins over the global `--path`) or the CWD as the target directory to **initialize**.

```bash
# A global option also works when placed after the subcommand
mem list --path /path/to/store

# A subcommand-level --path on init wins over the global --path:
# ./actual is initialized, not ./ignored, and ./ignored is never created
mem --path ./ignored init --path ./actual
```

### 1.3 Store layout

Layout created by `mem init`:

```text
<store root>/
├── .mem                 # JSON marker file that identifies the store root
├── .gitignore           # default ignore rules (created only when missing)
├── events/
│   └── YYYY-MM.jsonl    # event log: one file per month, append-only
└── projects/
    └── <project>/
        ├── files.jsonl  # this project's file records: append-only, can be rewritten by compact
        ├── meta.json    # project metadata (auto-created on first add, editable by hand)
        └── README.md    # project description generated by mem render
```

`.mem` is a JSON file that looks like this:

```json
{
  "created_at": "2026-10-22T13:05:52.992739415Z",
  "format": 1
}
```

Default `.gitignore` content written by `init`:

```gitignore
target/
*.swp
*.tmp
*.tmp.*
*~
.DS_Store
```

## 2. Exit codes and error behavior

| Exit code | Meaning | Output location and form |
| --- | --- | --- |
| `0` | Success | Normal results go to stdout |
| `1` | Runtime error | stderr prints `Error: <reason>` (multi-line errors continue on following lines); a `Warning:` may appear before `Error:` |
| `2` | Command-line argument parsing error (clap convention) | stderr prints `error: ...` plus `Usage:` / `For more information, try '--help'.` |

Key points:

- Runtime errors all flow through `run() -> Result`; `main` prints `Error: ...` and calls `std::process::exit(1)`. The success path exits with code 0.
- `query` with no filter at all is also a **runtime error** (exit code 1), with a two-line message:

```text
$ mem --path ./memory query
Error: No query filter specified.
Please specify at least one filter: --project (-p), --file-id, --filename (-n), or --fuzzy.
[exit code 1]
```

- A very small number of commands **print a heading to stdout first and then report an error on stderr** (for example, an invalid regex for `query --fuzzy`); scripts must handle the two streams separately:

```text
$ mem --path ./memory query --fuzzy '['
--- Regex fuzzy search: '[' ---          # stdout
Error: regex parse error:                 # stderr
    [
    ^
error: unclosed character class
[exit code 1]
```

- Argument parsing errors exit with code 2, for example:

```text
$ mem nope
error: unrecognized subcommand 'nope'

Usage: mem [OPTIONS] <COMMAND>

For more information, try '--help'.
[exit code 2]

$ mem --path ./memory add -p demo
error: the following required arguments were not provided:
  --summary <SUMMARY>
  <FILES>...

Usage: mem add --project <PROJECT> --summary <SUMMARY> <FILES>...

For more information, try '--help'.
[exit code 2]
```

- A Git conflict during `sync` is a **runtime error**: the command prints the steps it completed, tells you on stderr to run `mem resolve`, and exits with **code 1** (it no longer exits 0 on conflicts; see [3.6 sync](#36-sync)).
- An invalid project name is rejected before any store write, with exit code 1 and an `Error: invalid project name ...` message. A valid project name is a single path component: non-empty, not `.`/`..`, no `/`, `\`, or control characters, at most 200 bytes. It must also be representable on Windows: DOS device names (`CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9`, case-insensitive, including `con.txt`) and names ending in `.` are rejected, e.g. `Error: invalid project name "con": reserved Windows device name (would be invalid on Windows)` / `Error: invalid project name "foo.": must not end with '.' (would be invalid on Windows)`.

## 3. Subcommands

### 3.1 init

Initialize a new ACDM store.

**Usage**

```text
mem init [OPTIONS]
```

**Arguments**

| Short option | Long option | Required | Default | Description |
| --- | --- | --- | --- | --- |
| — | `--remote <URL>` | No | None | Also runs `git init` and adds an `origin` remote; the URL is not connectivity-checked and nothing is pushed |
| — | `--path <DIR>` | No | CWD | Directory to initialize; overrides the global `--path` |
| `-h` | `--help` | No | — | Print help |

**Behavior**

1. Create `<DIR>/events/` and `<DIR>/projects/`;
2. if `<DIR>/.mem` does not exist, write the marker file (`format: 1` plus creation time);
3. if `<DIR>/.gitignore` does not exist, write the default ignore rules;
4. if `--remote` is given: also run `git init` and `git remote add origin <URL>`.

Running `init` repeatedly is idempotent: an existing `.mem` and `.gitignore` are not overwritten, and the command still reports success. `init` does not configure git user identity; configure it yourself before `sync` (see [3.6 sync](#36-sync)).

**Example**

```bash
# Local-only store
mem init --path ./memory

# Also configure a Git remote: runs git init and adds origin
mem init --path ./memory --remote git@github.com:you/acdm-memory.git
```

**Real output**

```text
$ mem init --path ./memory
Successfully initialized ACDM store at: ./memory
Created directory structure:
  ├── events/       (Append-only event log)
  ├── projects/     (Project metadata and file records)
  └── .mem          (Store marker file; lets the CLI/MCP find the store from any subdirectory)

$ mem init --path ./memory --remote git@github.com:you/acdm-memory.git
Successfully initialized ACDM store with remote 'git@github.com:you/acdm-memory.git' at: ./memory
Created directory structure:
  ├── events/       (Append-only event log)
  ├── projects/     (Project metadata and file records)
  └── .mem          (Store marker file; lets the CLI/MCP find the store from any subdirectory)
```

Git state after `--remote` (verified in a separate directory):

```text
$ git -C ./memory remote -v
origin	git@github.com:you/acdm-memory.git (fetch)
origin	git@github.com:you/acdm-memory.git (push)
```

**Notes**

- `init` does not search upwards for an existing store; to initialize a subdirectory you must pass `--path` explicitly.
- `--remote` only adds a remote: it does not validate the URL, set branch tracking, or push. Before the first sync, the local repository needs at least one commit and an upstream branch (see [3.6 sync](#36-sync)).
- If `origin` already exists, running `--remote` again fails in `git remote add`, prints `Error: ...`, and exits with code 1.

### 3.2 add

Append one event (a summary plus a set of file records) to project memory.

**Usage**

```text
mem add [OPTIONS] --project <PROJECT> --summary <SUMMARY> <FILES>...
```

**Arguments**

| Short option | Long option | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `-p` | `--project <PROJECT>` | **Yes** | — | Project name (maps to `projects/<name>/`; must be a single safe path component, see Notes) |
| `-s` | `--summary <SUMMARY>` | **Yes** | — | Summary of this change |
| `-d` | `--device <DEVICE>` | No | Local hostname | Device name; when hostname is unavailable it falls back to `$HOSTNAME`, then `$COMPUTERNAME`, then `localhost` |
| `-a` | `--agent <AGENT>` | No | `human` | Recorder name |
| — | `<FILES>...` | **Yes** (at least 1) | — | File paths (relative to the CWD, or absolute); each must be a **regular file** (FIFOs, device nodes and directories are rejected) |
| — | `--path <DIR>` | No | Auto-discovered | Global option: store root directory |
| `-h` | `--help` | No | — | Print help |

**Behavior**

1. Validate the project name (a single safe path component; otherwise exit 1 with `Error: invalid project name ...`) **before touching the store**.
2. **Unlocked pre-computation** (this phase deliberately runs *before* the store lock, so slow file I/O never blocks other writers): for each `<FILES>` entry
   - normalize the file identity `file_name`: prefer relative to the store root; when the file is outside the store, relative to the nearest git repository root; then fall back to relative to the CWD; if none of these applies, keep the **absolute path** and print a warning to stderr. Existing path prefixes are canonicalized (symlinks resolved), so a symlinked store or project directory still yields a stable relative identity; a final symlink **to a file** keeps its own name (only its parent is canonicalized, 0.1.4), so a tracked in-repo symlink pointing outside the repository is still recorded as a repo-relative path;
   - **open the original path exactly once** (on Unix with `O_NONBLOCK`, so a FIFO swapped in can never block the command) and use that single handle for the `is_file()` check and for streaming SHA-256 in 64 KiB chunks (never loaded into memory as a whole); checking and hashing the same object closes the TOCTOU gap;
   - a path that is genuinely missing, or that disappears while being opened/hashed, becomes a `Deleted` candidate (`size_bytes = 0`, `hash = ""`) instead of an error — except a **dangling symlink** (the link exists but its target does not), which is a present file identity under Git link semantics: its content is the link target path as a slash-normalised string, `size_bytes` = that string's byte length, `hash` = its SHA-256 (0.1.5); a path that exists but is **not a regular file** (FIFO, device node, directory) aborts with `Error: cannot record '<path>': not a regular file`;
   - paths that normalize to the **same `file_name` within this batch** are collapsed into one record (the first occurrence wins — e.g. `a.txt a.txt` produces one `Created`, not two).
3. Take the store-wide cross-process write lock and, inside that one critical section, compare the prepared records with the latest `files.jsonl` snapshot to decide `Modified` / `Created`, then generate an independent `file_id` for each record. Because the hashing already finished, the lock is held only for the fast state transition (core API `record_file_event`), so the `Created` / `Modified` decision can never be based on a stale snapshot, a metadata write failure aborts the command instead of being ignored, and a slow file cannot stall `compact`/`resolve`/`sync` on the same machine.
4. Generate the event: `event_id` has the form `YYYYMMDDHHMMSS_nanos9_pid5_counter4` (UTC); `ts` is the fixed-width UTC timestamp with nanoseconds, `YYYY-MM-DDTHH:MM:SS.nnnnnnnnnZ`.
5. If `projects/<project>/meta.json` cannot be read (missing **or corrupt**), automatically write minimal metadata under the same lock: `description` is `"Project <name>"`, `github_url` is `null`, and `created_at` equals this event's time; a store damaged by a partial metadata write therefore self-heals here.
6. Append the event line to `events/YYYY-MM.jsonl`, and append each of this event's `FileRecord` entries to `projects/<project>/files.jsonl`. Both appends happen under the store-wide cross-process write lock.

**Notes**

- `<FILES>` is a required positional argument (at least one); each path may be relative to the CWD or absolute.
- The project name must be a single safe path component: non-empty, not `.`/`..`, no `/`, `\`, or control characters, at most 200 bytes; Windows-reserved device names (`CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9`, case-insensitive, including `con.txt`), names ending in `.`, and the Windows-invalid characters `<>:"|?*` are rejected as well. The CLI and MCP both reject anything else with `invalid project name`, so an agent-supplied name can never escape `projects/`, and a store created on Unix always checks out on Windows.
- `Created` / `Modified` is decided **solely** by whether `file_name` already appears in this project's `files.jsonl` (including historical records, after deduplication); content hashes are not compared, so even if a file's contents did not change, recording it a second time yields `Modified`.
- SHA-256 is computed by streaming in 64 KiB chunks **before the store lock is taken**, so recording a large file neither loads it into memory nor holds the store-wide lock during slow I/O; only the hash and byte count are stored.
- `add` only records **regular files**: a FIFO, device node or directory is rejected with `Error: cannot record '<path>': not a regular file` (exit 1), so a blocking/special file can never stall the store lock or produce a meaningless hash. A missing path — or one that disappears while being opened/hashed — is still recorded as `Deleted` (exit 0) instead of failing the whole command.
- **Dangling symlinks are not deletions** (0.1.5): a link whose target is missing is recorded with Git's symlink semantics — content = the link target path (slashes normalised), `size_bytes` = its byte length, `hash` = its SHA-256. Real output: `dangling.conf -> ../missing-target.txt` yields `[Created] dangling.conf (21 bytes, sha256: 0f1800ab...)` (the target string is `../missing-target.txt`, 21 bytes); recording it again yields `Modified`, and only deleting the link itself makes it `Deleted`. A **live** symlink is still followed and the target's content is hashed.
- Duplicate paths in one invocation are collapsed **after normalization**: `mem add ... a.txt ./a.txt` records a single `Created`/`Modified` entry for `a.txt` (0.1.3).
- A nonexistent file still produces a `Deleted` record, and its path is normalized by the same rules.
- A recorded absolute path will not match across devices and is only suitable for temporary local records; for cross-device scenarios, keep the file inside the store or inside some git repository (see the notes on legacy absolute-path records in [MIGRATION.md](MIGRATION.md)). The stderr warning covers Unix-style absolute paths (`/...`) and Windows drive paths (`C:/...`, checked with both `Path::is_absolute()` and a leading-`/` test).
- File contents themselves are never stored; only path, size, and SHA256 are kept.
- The event line is written to `events/` first, then to `projects/<p>/files.jsonl`; the two writes are not one atomic transaction, though they are consistent after a normal exit.

### 3.3 query

Query recorded events and file records.

**Usage**

```text
mem query [OPTIONS]
```

**Arguments**

| Short option | Long option | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `-p` | `--project <PROJECT>` | No | — | List all events for that project |
| — | `--file-id <FILE_ID>` | No | — | Look up a single file record by `file_id`, together with its parent event |
| `-n` | `--filename <FILENAME>` | No | — | **Exact-match** events by `file_name` (full relative path; no substring matching) |
| — | `--fuzzy <REGEX>` | No | — | Rust regex fuzzy search over the raw event JSON lines |
| — | `--path <DIR>` | No | Auto-discovered | Global option: store root directory |
| `-h` | `--help` | No | — | Print help |

**Argument constraint**: all four filters are optional, but **at least one** must be given; otherwise the command errors out with exit code 1. Multiple filters may be combined: output is emitted in the fixed order `--project` → `--file-id` → `--filename` → `--fuzzy` (with a blank line between sections).

**Index mechanism (in one sentence)**: `query` first scans every `events/*.jsonl` with `MemIndex` and records "file path + byte offset of the line start" for each event; on a hit it seeks back by offset and reads that line, so there is no persistent index and an in-memory index is rebuilt on every query.

```text
$ mem --path ./memory query --fuzzy 'zzz-not-present'

```

**Notes**

- `--file-id` matches `FileRecord.file_id` (every file record has its own ID); the output includes the full details of the parent event.
- `-n/--filename` matches the **normalized relative `file_name`** (e.g. `src/hello.txt`) and is a **whole-string exact match**, not a substring search (querying `hello.txt` will not match `src/hello.txt`); it is not a system absolute path. Legacy records that store absolute paths cannot be found by relative name (see [MIGRATION.md](MIGRATION.md)).
- `--fuzzy` runs a Rust `regex` match against the raw JSONL line of each event; it is not full-text tokenization. With an invalid regex it prints the search heading first, then reports `Error: regex parse error: ...` on stderr and exits with code 1.
- Filters can be combined; output order is fixed as project → file_id → filename → fuzzy.
- Every query rescans the event files to build the index; queries get slower as the store grows. This is a known characteristic of the current implementation, not a resident service.

### 3.5 compact

Compact project file records: rebuild `files.jsonl` from the append-only event log, keeping only the latest record per `file_name`.

**Usage**

```text
mem compact [OPTIONS] --project <PROJECT>
```

**Arguments**

| Short option | Long option | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `-p` | `--project <PROJECT>` | **Yes** | — | Project to compact |
| — | `--path <DIR>` | No | Auto-discovered | Global option: store root directory |
| `-h` | `--help` | No | — | Print help |

**Behavior**

1. Validate the project name.
2. Take the store-wide cross-process write lock and hold it through the rename below.
3. Count the non-empty lines of the existing `projects/<project>/files.jsonl` as `records_before` (0 when the file does not exist).
4. Read the **event log** (`events/*.jsonl`), keep this project's events, sort them by `ts` (parse-aware) with `event_id` as the tie-breaker, and replay every `FileRecord`: the last writer for each `file_name` wins. The result is the complete latest-state projection. Note the deliberate asymmetry: incremental `add`/`resolve` writes follow the physical append (causal) order, while this replay orders by timestamp first.
5. Write it to a temporary file `files.jsonl.tmp` in the same directory (`flush` + `sync_all`), then atomically `rename` it over the original file. If neither the projection nor any event exists, return `0/0` without creating a directory.
6. Print the record counts before and after compaction and the number pruned.

Because the projection is rebuilt from the event log, `compact` is also a **self-healing** operation: after a crash (or an old 0.1.0 race) that left `files.jsonl` missing, truncated, or stale, one `compact` restores the correct latest state. Because the whole sequence holds the store write lock, a concurrent `mem add` on the same machine waits instead of being lost.

**Real output**

The setup recorded: two records for `src/hello.txt` (Created + Modified), one for `src/util.txt`, and one for `src/removed.txt` — 4 records in total:

```text
$ mem --path ./memory compact -p demo
Compacting file records for project 'demo'...
Compaction completed for project 'demo':
  Records before: 4
  Records after:  3
  Records pruned: 1
```

The three `mem list -p demo` rows after compaction (identical to before compaction, because `list` already shows only the latest records):

```text
$ mem --path ./memory list -p demo
FILE NAME                        ACTION     SIZE (BYTES)   FILE ID                               HASH (SHA256)
-----------------------------------------------------------------------------------------------------------------------------
src/hello.txt                    Modified   15             20261022130617_174840512_23161_0000   a56bd9a88d975841...
src/removed.txt                  Deleted    0              20261022130617_177470336_23163_0000   -
src/util.txt                     Created    12             20261022130617_176154452_23162_0000   f957b19529906961...
```

**Notes**

- `compact` rewrites only `projects/<project>/files.jsonl` and **never touches `events/`**; historical events remain fully queryable via `query`.
- After the rewrite, records in the file are ordered by `file_name` (internally a `BTreeMap`), not in the original append order.
- The number pruned is `records_before - records_after` (computed and printed by the CLI). `records_before` counts the lines of the *old projection*, so a projection that was lost/truncated by a crash reports a smaller `before` count and the healed result is still complete.
- The temp-write-plus-atomic-rename means an interrupted process leaves at most a `files.jsonl.tmp` behind (already covered by the store `.gitignore`'s `*.tmp`).
- Since 0.1.1 `compact` holds the store-wide write lock and reads the event log, so it cannot lose a concurrent `mem add` on the same machine and can be used to repair a stale projection; on different machines, coordinate through `sync` as usual.

### 3.6 sync

Commit local store changes, pull remote updates with rebase, then push back to the remote.

**Usage**

```text
mem sync [OPTIONS]
```

**Arguments**

| Short option | Long option | Required | Default | Description |
| --- | --- | --- | --- | --- |
| — | `--path <DIR>` | No | Auto-discovered | Global option: store root directory |
| `-h` | `--help` | No | — | Print help |

**Behavior (strictly in execution order)**

1. Resolve the store root and take the **store-wide cross-process write lock**, which is held for the whole command. Then run `git status --porcelain` at the store root; if this is not a git repository or git is unavailable → `Error: ...`, exit 1.
2. If the working tree is **not clean**: `git add -A`, then `git commit -m "Auto-sync from <device> at <ts>"`, where `<device>` is the local hostname (same rules as `add`) and `<ts>` is the fixed-width UTC nanosecond timestamp. All local changes are committed *before* the pull, so the pull always starts from a clean tree.
3. If the current branch has an upstream: `git pull --rebase` (**no `--autostash`**).
   - pull succeeds → record the step `Pulled remote changes with rebase`;
   - pull fails and conflicts are detected (unmerged files, porcelain conflict codes, or active rebase/merge state — Git's bookkeeping only, file contents are never scanned) → record the completed steps, print a warning on **stderr** telling you to run `mem resolve`, then return `Error: sync stopped on a git conflict: ...` and exit **1**. Nothing is pushed;
   - pull fails for a non-conflict reason (network/authentication/index problems) → **abort the sync** with `Error: git pull --rebase failed and the repository is not conflicted; aborting sync instead of pushing over an inconsistent state: ...`, exit 1. Nothing is pushed.
4. If the branch has no upstream: record the step `No upstream configured; skipped pull` (the push is still attempted).
5. `git push`; on failure `Error: ...`, exit 1. On success print the completed steps followed by `✅ Sync successful: repository is up-to-date and pushed to remote.`

Note that the completed steps are printed on **success** and on a **conflict**; on other runtime errors only the `Error:` line appears.

**Notes**

- Prerequisites: the store root is a git repository and git user identity is configured (`user.name` / `user.email`); if the working tree needs a commit and identity is missing, the commit fails and the command exits 1. A usable push target is required for success; an upstream is optional (without one the pull is skipped).
- On conflict the command **does not** auto-merge and **does not** abort the rebase; it leaves the conflict state to `mem resolve`. Since 0.1.1 a conflicted sync exits with **code 1**, so scripts can rely on the exit code; MCP's `mem_sync` reports the same situation as an `isError` result.
- No `--autostash`: the tree is committed before the pull and the store write lock is held, so there is nothing to stash. Removing autostash avoids the hard-to-recover state where a stash pop conflicts in the middle of a rebase.
- A non-conflict pull failure aborts the sync (no push); the error is surfaced instead of being swallowed.
- The commit message is fixed to `Auto-sync from <device> at <ts>`; `sync` offers no custom-message argument (MCP's `mem_sync` supports an optional `message`, but its **default is the same** `Auto-sync from <device> at <ts>`; see [MCP.md](MCP.md)). Both entry points share the one default inside `sync_store`.
- While `sync` runs, the store write lock prevents local `add` / `compact` / `resolve` from interleaving; other devices are not locked (cross-device coordination is the Git remote's job).
- Git's error text depends on locale; the examples use `LC_ALL=C`, and the content itself is raw git output.
- `sync` does not invoke any conflict-resolution logic (it never runs `resolve` automatically), nor does it create a remote; remotes are configured only by `mem init --remote` or manual git commands.

### 3.7 resolve

Scan all `.jsonl` files in the store for Git conflict markers, deduplicate and sort records, and continue the rebase.

**Usage**

```text
mem resolve [OPTIONS]
```

**Arguments**

| Short option | Long option | Required | Default | Description |
| --- | --- | --- | --- | --- |
| — | `--path <DIR>` | No | Auto-discovered | Global option: store root directory |
| `-h` | `--help` | No | — | Print help |

**Behavior**

1. Take the store-wide cross-process write lock (held for the whole command), then recursively scan every `*.jsonl` under the store (`hidden(false)`: hidden files are scanned too; `.gitignore` filtering applies when the store is a git repository).
2. Work on **raw bytes** (`fs::read`), so invalid UTF-8 bytes and CRLF line endings are preserved byte-for-byte; only lines that are exactly Git conflict markers are treated as markers — `=======` must be the whole line, and `<<<<<<<` / `|||||||` / `>>>>>>>` must be followed by end-of-line or a space. A data line that merely starts with marker-like characters is kept.
3. For each file that contains a marker: strip the exact marker lines, detect the record kind (`Event` / `FileRecord` / other JSON / unrecognized) and handle each accordingly:
   - valid records are deduplicated by key (`event_id` / `file_id`), and **the later occurrence wins**;
   - event records are sorted by parsed timestamp (old formats are supported), with `event_id` as the tie-breaker; file records **keep their original causal order** (only the last occurrence of each `file_id` is kept, at its original position); other valid JSON records are sorted by `ts` (when present) and then by deduplication key;
   - **anything that cannot be parsed as the corresponding record kind is preserved verbatim as raw bytes** (including original whitespace and non-UTF-8 bytes) and placed at the end of the file; identical preserved lines are deduplicated;
   - valid records are **re-emitted with their original raw line text**, so unknown fields, field order, and formatting are never lost.
4. Write the resolved file back (holding an exclusive file lock); when the store is a Git repository (detected with `git rev-parse --git-dir`, so linked worktrees and submodules whose `.git` is a **file** work too), run `git add -- <relative path>` for every rewritten file. A failed `git add` is a **hard error** (the following `rebase --continue` could never succeed, and a warning would hide the real cause).
5. If a rebase is in progress (Git state paths resolved via `git rev-parse --git-path`; detection never relies on git's localized error text), run `git rebase --continue` (with `GIT_EDITOR=true` to avoid blocking on an editor) and **repeat from step 1** — a rebase replaying several conflicting commits is advanced to completion in this single invocation, up to 100 rounds.
6. Stop when no rebase is active (report totals across all rounds). If `git rebase --continue` fails: when every still-unresolved file is a `.jsonl` file and progress was made in the round, keep going; when this round actually resolved at least one JSONL conflict (`resolved_this_round > 0`, 0.1.5), nothing is unresolved, and the **index is clean** (`git diff --cached --quiet` = no staged difference from `HEAD`; neither untracked scratch files nor unstaged edits to unrelated tracked files block recovery), the replayed commit became an **empty patch** after deduplication (all its records already exist upstream), so it is dropped with `git rebase --skip` and the rebase continues — otherwise (rebase paused for an unrelated reason) Git's original error is returned instead of a silent skip; otherwise print an actionable error listing the **non-JSONL** files (e.g. `projects/<p>/meta.json`) that must be resolved manually with `git add <file>` and `git rebase --continue`. The unresolved list is read via `git diff --name-only --diff-filter=U -z`, so paths with spaces or special characters are reported verbatim (no git quoting).

**Real output (hand-crafted conflict file outside a git directory: one unparseable truncated line)**

**Notes**

- `resolve` resolves only `.jsonl` files and **does not handle non-JSONL conflicts**, for example `projects/<p>/meta.json` (which can conflict when two devices write metadata for the same new project at the same time). Those must be resolved manually and `git add`ed. However, a JSONL-only conflict no longer stops the command: it keeps resolving and continuing the rebase until it finishes. The command fails (exit 1) only when a genuinely non-JSONL file is still conflicted, and then it prints an actionable error listing the still-unresolved paths and telling you to `git add <file>` and retry; see [TROUBLESHOOTING.md](TROUBLESHOOTING.md) for troubleshooting.
- It also works outside a git repository: it merely strips conflict markers, without `git add` and without continuing a rebase.
- The whole operation holds the store write lock, so it cannot interleave with a local `add`, `compact`, or `sync`.
- Preserved lines are never silently discarded — this now holds at the byte level, including invalid UTF-8 and CRLF content; valid historical records are never rewritten either (apart from conflict markers, deduplication, and sorting, the raw line text stays as-is).
- Deduplication is "the later occurrence wins": in a rebase scenario this usually means the record from the `theirs` branch replaces the same-ID record from `ours`. `FileRecord`s keep their original causal order instead of being re-sorted, so the last-write-wins projection cannot be rolled back to an older state.
- `Files updated` shows absolute paths. The report counts are aggregated over all rebase rounds performed by the single invocation.
- A replayed commit that becomes an **empty patch** after de-duplication is skipped automatically with `git rebase --skip` (0.1.2). Since 0.1.4 the decision is **index-based** (`git diff --cached --quiet`): only staged content counts, so untracked scratch files and unstaged edits to unrelated files in the store no longer prevent the rebase from finishing — and they are not committed by the resolver. Since 0.1.5 the skip additionally requires that **this round actually resolved JSONL conflicts** (`resolved_this_round > 0`): if the rebase stopped for an unrelated reason (`git rebase --exec` failure, `edit`, a failed commit signature, ...), `mem resolve` returns Git's original error instead of silently discarding your commit. Note that `git rebase --skip` may itself reset unstaged changes to unrelated files in the working tree; that is Git's behaviour, not something the resolver preserves. Otherwise git's "No changes - did you forget to use `git add`?" would stop the loop on a commit that should simply be dropped.
- The unresolved-file list comes from `git diff --name-only --diff-filter=U -z`: NUL-separated raw paths, so a file name containing spaces or special characters is reported (and checked for the `.jsonl` suffix) without git's quote/escape rendering.
- Works in `git worktree` / submodule checkouts (`.git` is a file) and treats a failed `git add` as a hard error instead of a warning.

### 3.8 render

Generate or update a project's `README.md` (`projects/<project>/README.md`).

**Usage**

```text
mem render [OPTIONS] --project <PROJECT>
```

**Arguments**

| Short option | Long option | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `-p` | `--project <PROJECT>` | **Yes** | — | Project name to render |
| — | `--path <DIR>` | No | Auto-discovered | Global option: store root directory |
| `-h` | `--help` | No | — | Print help |

**Behavior**

1. Validate the project name (must be a single safe path component).
2. Read `projects/<project>/meta.json`; **if reading fails**, use in-memory fallback metadata (`name` = project name, `description` = `"Project <name>"`, `github_url` = null, `created_at` = current time) and **do not write `meta.json` back**;
3. take the latest record per `file_name` for that project to build the file table;
4. take the project's 10 most recent events to build the timeline (newest first);
5. take the store-wide cross-process write lock, then write `projects/<project>/README.md` (creating the directory if needed), overwriting it every time — rendering cannot dirty the work tree in the middle of a `sync` rebase. Every interpolated value is escaped: `|` becomes `\|` and CR/LF are folded to spaces, so recorded summaries/file names/metadata cannot break the table or inject extra Markdown lines.

```markdown
# <project>

- **GitHub:** <github_url>        # only when meta.github_url exists

## Tracked Files

| File Name | Action | Size (bytes) | Hash (SHA256) |
| --- | --- | --- | --- |
| ... | ... | ... | ... |

## Recent Activity Timeline

- **<ts>** [`<agent>` on `<device>`]: <summary>   # the 10 most recent, newest first
```

**Notes**

- `render` is a pure generation operation: it overwrites `projects/<project>/README.md` every time and never modifies `files.jsonl` / `meta.json` / `events/`.
- Table cells and timeline fields are escaped (`|` → `\|`, CR/LF → space), so a recorded summary or file name that contains a pipe or a newline cannot break the generated Markdown structure or inject content.
- A missing `meta.json` only affects that render run and is not backfilled; only a subsequent `mem add` (or MCP's `mem_add_event`) auto-creates `meta.json`, at which point `CREATED AT` / `DESCRIPTION` in `list` change from `-` to real values.
- An empty hash renders as two backticks (`` `` ) in the table; this is the actual output of the current format.
- The timeline is capped at 10 entries; events are read in ascending time order and then reversed to newest-first.

## 4. Environment variables

| Variable | Effect | Description |
| --- | --- | --- |
| `ACDM_STORE` | Store discovery | Used as the store root when no `--path` is given; lower priority than `--path`, higher than upward search. `init` does not use it (`init` only looks at `--path` or the CWD) |
| `XDG_RUNTIME_DIR` | Store write-lock location | Directory for the store-wide advisory lock file (`acdm-store-<hash>.lock`, keyed by the canonical store path). When unset or not a directory, the system temp directory is used. The lock file is never inside the store or the Git repository |
| `HOSTNAME` / `COMPUTERNAME` | Default device name | Fallback sources for the device name in `add` / `sync`: first try the `hostname` command, then read these two variables in order, and finally fall back to `localhost` |
| `PATH` | `sync` / `resolve` | The `git` executable must be findable |
| git-related variables (`GIT_AUTHOR_NAME`, `GIT_COMMITTER_*`, `GIT_EDITOR`, and so on) | git commit behavior | Both `sync`'s commit and `resolve`'s `rebase --continue` inherit the environment; `resolve` hard-codes `GIT_EDITOR` to `true` internally |
| `LC_ALL` / `LANG` | Error-message language | Localizes the git subprocess's stderr; the examples use `LC_ALL=C` to get English errors |

`ACDM_STORE` example (real output):

```text
$ ACDM_STORE=/path/to/store mem list

------------------------------------------------------------------------------------------------
demo                     4        2026-10-22T13:06:17.173539195Z   Project demo
```

## 5. Common workflows

### 5.1 Everyday single-machine use

```bash
# 1) Initialize (once)
mem init --path ./memory

# 2) Record changes
mem --path ./memory add -p ACDM -s "实现增量索引" -d laptop -a claude src/index.rs src/storage.rs

# 3) Query / browse
mem --path ./memory query -p ACDM
mem --path ./memory query -n src/index.rs
mem --path ./memory list
mem --path ./memory list -p ACDM

# 4) Generate the project description
mem --path ./memory render -p ACDM

# 5) Periodically rebuild the files.jsonl projection (also heals a stale/missing one)
mem --path ./memory compact -p ACDM
```

### 5.2 Cross-device sync

```bash
# Device A: initialize the store and configure the remote
mem init --path ./memory --remote git@github.com:you/acdm-memory.git
cd ./memory
git add -A && git commit -m "initial store"
git push -u origin HEAD
cd ..

# Device B: clone the same store
git clone git@github.com:you/acdm-memory.git ./memory

# Both devices work through add / sync (git user identity must be configured first)
mem --path ./memory add -p ACDM -s "change on A" -d laptop-a -a claude src/index.rs
mem --path ./memory sync

# Common conflict handling (see 5.3)
mem --path ./memory sync        # if stderr reports a conflict
mem --path ./memory resolve
mem --path ./memory sync
```

### 5.3 Conflict recovery

```bash
# 1) After sync reports a conflict (exit code 1), see which files actually conflict
mem --path ./memory sync
git -C ./memory status --porcelain

# 2) Resolve JSONL conflicts automatically: one call strips markers, deduplicates,
#    preserves unparseable bytes, and keeps advancing the rebase until it finishes
mem --path ./memory resolve

# 3) Normally the rebase is now complete and step 2 already ran git rebase --continue.
#    Only if resolve reported non-JSONL files (e.g. meta.json) still conflicted:
git -C ./memory add projects/<project>/meta.json
git -C ./memory rebase --continue

# 4) Sync again (exit code 0 once the conflict is gone)
mem --path ./memory sync
```

### 5.4 Adopting an existing project from scratch

It is recommended to keep the store as a **standalone Git repository** (separate from the code repository) and record files from the code repository:

```bash
# 1) Create the store anywhere (it is an independent sync unit)
mem init --path ~/acdm-memory --remote git@github.com:you/acdm-memory.git

# 2) Develop in the code repository as usual, recording changes with add
#    When a file is outside the store, file_name is normalized to a path relative to the nearest git repository root,
#    so it keeps the same identity across devices and mount points
cd ~/src/my-project
mem --path ~/acdm-memory add -p my-project -s "add parser" -d laptop -a claude src/parser.rs

# 3) Query and render
mem --path ~/acdm-memory query -p my-project
mem --path ~/acdm-memory render -p my-project
```

If you want to set `github_url` / `description` in `meta.json`, edit `projects/<project>/meta.json` by hand and then run `render`.

### 5.5 Scripting

- Use exit codes to determine the outcome: `0` success; `1` runtime error; `2` argument error. Note that `sync` also returns 0 on conflict (an extra check is required).
- Command output is written for humans; there is **no machine-readable output mode such as `--json`**. If a script needs structured data, read the store's `events/*.jsonl` and `projects/<p>/files.jsonl` directly (format described in [README.md](../README.md)).
- Errors go to stderr and normal results to stdout; handle the two streams separately (for example, an invalid `query --fuzzy` regex prints its stdout heading before reporting the error on stderr).
