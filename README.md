# ACDM — Agent Cross-Device Memory System

[![CI](https://github.com/Jerry-Hang/acdm/actions/workflows/ci.yml/badge.svg)](https://github.com/Jerry-Hang/acdm/actions/workflows/ci.yml)

*ACDM (Agent Cross-Device Memory System) is a serverless, cross-device memory layer for AI agents that work on the same project from different machines. It records project events as append-only, month-sharded JSONL and synchronizes them through Git, so every machine sees the same history without running a database or a hosted backend. One Rust workspace ships two entry points: the `mem` CLI for humans and scripts, and `mem-mcp`, a stdio MCP server for agents. Timestamps and IDs are fixed-width UTC, file paths are normalized into repo-relative identities, and JSONL merge conflicts are resolved automatically by `mem resolve` — preserve-first, never silently dropping data. The project is MIT-licensed and currently at v0.1.5.*

ACDM gives cross-device AI agents a shared project memory through **Git sync + append-only JSONL**: an agent records events on any machine, and after syncing, another machine can look up the same history.

- **Git sync**: the store directory is maintained as a Git repository, and `mem sync` commits every local change, pulls with rebase, and pushes. A conflict stops the sync with a non-zero exit (MCP: `isError`), and a non-conflict pull failure aborts instead of pushing over it.
- **append-only JSONL**: events are appended month by month, so history only grows and is never rewritten; the read side tolerates corrupt lines, and a single bad line does not break the whole store.
- **SHA256 tracking**: every file record carries `size_bytes` and a SHA256 `hash`, which can be used to tell whether file contents changed; `mem add` hashes files in 64 KiB chunks instead of loading them whole.
- **Automatic conflict resolution**: `mem resolve` removes only exact Git conflict markers, de-duplicates by `event_id` / `file_id` (last write wins, causal order preserved), keeps unparseable lines and non-UTF-8 bytes verbatim, preserves unknown fields, and advances a multi-commit rebase in one call.
- **CLI + MCP entry points**: humans and scripts use the `mem` command line; AI agents connect through `mem-mcp` (a stdio MCP server).

## Data layout

The root directory structure of an ACDM store (created by `mem init`):

```
<store root>/
├── .mem                       # marker file identifying the store root
├── .gitignore                 # default ignore rules generated by init
├── events/
│   └── YYYY-MM.jsonl          # event log, one file per month, append-only
└── projects/
    └── <project>/
        ├── files.jsonl        # file records for this project, append-only
        ├── meta.json          # project metadata
        └── README.md          # project description generated by mem render
```

The first `mem init` writes the `.mem` marker file at the store root; both `mem` and `mem-mcp` rely on it (or the `events/` directory) to discover the nearest store by walking upward from the current directory. `.mem` is a JSON marker file that looks like:

```json
{
  "format": 1,
  "created_at": "2026-10-22T13:02:45.123456789Z"
}
```

The store root should be used as an **independent Git repository** (`mem init --remote <url>` runs `git init` and adds `origin` automatically); `mem sync` needs a usable remote and push credentials configured on the repository. It is recommended to treat the whole store directory (rather than some subdirectory) as the unit of synchronization.

### Data structures

Event `Event` (one JSONL line):

| Field | Type | Description |
| --- | --- | --- |
| `event_id` | string | Event ID, format `YYYYMMDDHHMMSS_nanos9_pid5_counter4` (UTC) |
| `ts` | string | Event time, fixed-width UTC nanoseconds: `YYYY-MM-DDTHH:MM:SS.nnnnnnnnnZ` |
| `device` | string | Device name, defaulting to the hostname for the CLI |
| `agent` | string | Recorder: CLI defaults to `human`, MCP defaults to `mcp-agent` |
| `project` | string | Project name |
| `summary` | string | Change summary |
| `files` | `FileRecord[]` | File records associated with this event |

File record `FileRecord` (elements of the `files` array, also appended to `projects/<project>/files.jsonl`):

| Field | Type | Description |
| --- | --- | --- |
| `file_id` | string | File record ID, same format as `event_id` |
| `file_name` | string | Store / Git-repository-relative path, `/`-separated, the cross-device file identity |
| `action` | string | `Created` / `Modified` / `Deleted` |
| `size_bytes` | number | File size in bytes; `0` when `Deleted` |
| `hash` | string | SHA256 hex digest; empty string when `Deleted` |

Project metadata `ProjectMeta` (`meta.json`):

| Field | Type | Description |
| --- | --- | --- |
| `name` | string | Project name |
| `description` | string | Project description |
| `github_url` | string \| null | Associated repository URL, optional |
| `created_at` | string | Creation time |

An example event record (field definitions are authoritative in `mem-core/src/models.rs`):

```json
{"event_id":"20261022130245_123456789_01234_0001","ts":"2026-10-22T13:02:45.123456789Z","device":"laptop","agent":"claude-code","project":"ACDM","summary":"实现增量索引","files":[{"file_id":"20261022130245_123456790_01234_0002","file_name":"src/index.rs","action":"Created","size_bytes":4096,"hash":"2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824"}]}
```

## Store discovery rules

The `mem` CLI and `mem-mcp` use the **same** discovery logic (`mem-core/src/util.rs`), in priority order from highest to lowest:

1. Explicit path: the CLI's global `--path <dir>`; the MCP's start-up `--path <dir>`.
2. The `ACDM_STORE` environment variable.
3. Walking upward from the current working directory for the nearest store root (a directory containing a `.mem` marker file, or containing an `events/` directory).
4. Fallback: the current working directory.

`init` is the exception: it uses `--path` to designate the directory to **initialize**, and uses the current working directory when not specified.

## CLI quick start

The commands below assume `mem` is on `PATH` (or replace it with the absolute path to `target/release/mem`).

### 1. Initialize a store

```bash
# Local store only
mem init --path ./memory

# Also configure a Git remote: runs git init and adds origin
mem init --path ./memory --remote git@github.com:you/acdm-memory.git
```

### 2. Record an event

```bash
mem --path ./memory add \
  -p ACDM \
  -s "实现增量索引" \
  -d laptop \
  -a claude-code \
  src/index.rs src/storage.rs
```

- `files` is a required positional argument; multiple files can be passed at once.
- `-p/--project` and `-s/--summary` are required.
- `-d/--device` defaults to the hostname; `-a/--agent` defaults to `human`.
- File paths are normalized to store / Git-repository-relative paths before being written; a file that does not exist is recorded as `Deleted` (`size_bytes` 0, empty `hash`).

### 3. Query

```bash
# All events of a project
mem --path ./memory query -p ACDM

# Look up a file record by exact file_id
mem --path ./memory query --file-id 20261022130245_123456790_01234_0002

# Exact filename match (pass the relative path from the record; full-string match)
mem --path ./memory query -n src/index.rs

# Regex fuzzy search over all event lines
mem --path ./memory query --fuzzy '索引|index'
```

`query` needs at least one filter (`-p`, `--file-id`, `-n`, or `--fuzzy`), otherwise it errors out.

### 4. List projects and file state

```bash
# All projects
mem --path ./memory list

# Current file state of a project (only the latest record per file_name)
mem --path ./memory list -p ACDM
```

### 5. Compact file records

```bash
mem --path ./memory compact -p ACDM
```

`files.jsonl` is a **projection rebuilt from the append-only event log**: `compact` holds the store-wide write lock, replays every event in time order, keeps the last writer per `file_name`, and atomically replaces the file via a temporary file + rename. Running it also heals a projection that a crash left missing or truncated, and it cannot lose records appended concurrently.

### 6. Render a project README

```bash
mem --path ./memory render -p ACDM
# Generates projects/ACDM/README.md (metadata + file table + recent events)
```

### 7. Sync and conflict resolution

```bash
# Sync: commit all local changes, then pull --rebase (no autostash), then push
mem --path ./memory sync

# If sync reports a conflict: automatically clean up conflict markers in JSONL
mem --path ./memory resolve

# Sync again after resolving
mem --path ./memory sync
```

`sync` commits first and holds the store write lock for the whole operation. It skips the pull when the branch has no upstream, and it aborts (non-zero exit) when a non-conflict pull error occurs instead of pushing over an inconsistent state. When the pull hits a Git conflict, it does not merge automatically: it prints the completed steps, tells you to run `mem resolve`, and exits non-zero. `resolve` runs `git rebase --continue` only while a rebase is actually in progress (`.git/rebase-merge` or `.git/rebase-apply`), and a single call keeps resolving and continuing until the rebase finishes (up to 100 rounds).

## MCP integration

`mem-mcp` is a stdio MCP server (JSON-RPC 2.0) launched by an MCP client; it does not need to run as a daemon.

### Client configuration example

A generic JSON configuration (`command` is the absolute or relative path to `mem-mcp`; the **optional** `--path` in `args` specifies the store):

```json
{
  "mcpServers": {
    "acdm": {
      "command": "/path/to/target/release/mem-mcp",
      "args": ["--path", "/path/to/store"]
    }
  }
}
```

You can also specify the store with the `ACDM_STORE` environment variable:

```json
{
  "mcpServers": {
    "acdm": {
      "command": "mem-mcp",
      "args": [],
      "env": {
        "ACDM_STORE": "/path/to/store"
      }
    }
  }
}
```

When neither `--path` nor `ACDM_STORE` is given, the store is discovered from the current working directory upward using the same rules as the CLI. `mem-mcp` checks the store at startup; if the target directory is not yet a store, it creates the directory structure and writes the `.mem` marker file automatically (equivalent to `mem init`).

### Tool list

| Tool | Arguments | Description |
| --- | --- | --- |
| `mem_get_context` | `project?` | Lists all projects when `project` is omitted; otherwise returns project metadata, `README.md`, and the 5 most recent events |
| `mem_add_event` | `project`, `summary`, `device?`, `agent?`, `files?` | Records an event; `agent` defaults to `mcp-agent`, `device` defaults to the current hostname |
| `mem_query` | `by`, `value` | `by` is one of: `project` / `file_id` / `filename` / `fuzzy` |
| `mem_list_projects` | none | Lists all projects |
| `mem_compact` | `project` | Rebuilds the project's `files.jsonl` projection from the event log (also heals a missing/stale projection) |
| `mem_sync` | `message?` | Commit all changes (default message `Auto-sync from <device> at <ts>`, identical for CLI and MCP), pull with rebase (no autostash), push; conflicts and failures come back as `isError` results |
| `mem_resolve` | none | Automatically resolves JSONL conflicts, advancing a multi-commit rebase in one call |
| `mem_render` | `project` | Generates `projects/<project>/README.md` |

`mem_add_event`'s `files` is an array whose elements follow `FileRecord`: `file_name` (required), `action` (optional; exactly `Created` / `Modified` / `Deleted`, defaults to `Modified`), `size_bytes`, `hash`. If `file_name` is an absolute path, it is first normalized to a store / Git-repository-relative path before being written, so it can match across devices. Project names must be a single safe path component (non-empty, not `.`/`..`, no `/`, `\`, or control characters, at most 200 bytes); Windows-reserved device names (`CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9`, case-insensitive, including `con.txt`), names ending in `.`, and the Windows-invalid characters `<>:"|?*` are rejected too, so a store synced from Unix always checks out on Windows. CLI and MCP both reject anything else.

Protocol-level problems use JSON-RPC errors (`-32700` malformed JSON, `-32600` invalid request such as a wrong `jsonrpc` version or an over-long request line, `-32601` unknown tool/method, `-32602` invalid tool arguments). Tool-level failures (git conflict, invalid query dimension, unsafe project name, a failed sync, ...) are returned as a normal response with `result.isError = true` and a readable message, so an agent can correct itself and retry. A single request line is capped at 16 MiB; an oversized line is rejected with `-32600` and the server keeps serving.

## Design highlights

For the complete architecture and trade-offs, see [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) and [docs/DESIGN.md](docs/DESIGN.md) respectively.

### Timestamps

Every entry point writes the same **fixed-width UTC nanosecond** format:

```
YYYY-MM-DDTHH:MM:SS.nnnnnnnnnZ   // exactly 30 characters, UTC
```

Fixed width means string order equals time order, so plain string sorting is chronological. Two legacy formats exist in historical data (second-precision `...Z` and nanosecond `...+00:00`); the read side parses both, sorts by parsed time (`ts_cmp`), and places unparseable timestamps after parseable records to keep results deterministic.

### IDs

`YYYYMMDDHHMMSS_nanos9_pid5_counter4`:

- The timestamp is **UTC**, so IDs written by devices in different time zones still sort consistently.
- Fixed-width fields guarantee that lexicographic order is chronological order.
- Nanoseconds + pid + an in-process counter make cross-device collisions extremely unlikely (the old format had only seconds + pid + at most 100 counts, so two devices could generate the same ID and conflict resolution would mistake them for "the same record"). The counter starts from a random offset derived from the process start time and pid, which lowers the collision odds further in containers where every process has pid 1; the ID format is unchanged.

### File identity

`file_name` is normalized into a stable cross-device identity, in priority order:

1. Relative to the store root (e.g. `src/index.rs`);
2. Relative to the nearest Git repository root (when the file is outside the store);
3. Relative to the current working directory;
4. When none of the above applies, fall back to an absolute path.

The longest on-disk-existing prefix of a path is canonicalized (symbolic links resolved), and the still-missing tail is appended lexically, so a store or file reached through a symlink keeps the same identity as its real path. One deliberate exception: a final symbolic link **to a file** keeps its own name (only its parent directory is canonicalized), so a tracked in-repo symlink pointing outside the repository is still recorded under its repo-relative path instead of degrading to an absolute path; symlinks to directories (a symlinked store root or parent directory) are still resolved. A **dangling** symlink (the link exists, its target does not) is recorded the way Git stores a symlink: the content is the link target path as a slash-normalised string, `size_bytes` is that string's byte length and `hash` is its SHA-256 — so the link is `Created`/`Modified` rather than being mistaken for a deletion, while a live symlink still follows its target and hashes the target's content. A `\` in a path is replaced with `/`, and `.` / `..` are resolved lexically (the file need not exist).

### Conflict resolution guarantees

`mem resolve` handles Git conflict markers in all `.jsonl` files:

- Removes only the exact marker shapes Git writes (`=======` must be exactly that line; `<<<<<<<` / `>>>>>>>` / `|||||||` must be followed by end-of-line or a space), so a data line that merely starts with marker-like characters is preserved;
- Works on raw bytes, so unparseable lines — including invalid UTF-8 and CRLF endings — are preserved verbatim, never silently dropped;
- De-duplicates records with the same `event_id` / `file_id`, with **later occurrences (theirs) overriding earlier ones (ours)** and `FileRecord`s kept in causal order;
- Re-emits the raw line text of known records as-is, **preserving unknown fields, field order, and formatting**;
- Runs `git rebase --continue` only when a rebase is actually active (`git rev-parse --git-path` state, so linked worktrees and submodules with a `.git` *file* work too), avoiding reliance on Git's localized error messages, and loops through a multi-commit rebase (up to 100 rounds) in a single call;
- When de-duplication turns a replayed commit into an **empty patch**, that commit is dropped automatically with `git rebase --skip` instead of stopping with Git's "No changes" error; a failed `git add` is a hard error (it would only hide the real cause of a doomed `rebase --continue`).

### Concurrency and reads

- Every write operation (event append, projection rebuild, README render, `init`, conflict resolution, sync) takes a **store-wide cross-process write lock** (`fs2` advisory lock). Once the `.mem` marker exists, the lock is an advisory `flock` on that marker opened **read-only** — nothing is written, the Git work tree stays clean, and the store's own file permissions scope the lock. A store without a marker yet (only the very first `init`) falls back to an owner-only (`0600`) lock file in `$XDG_RUNTIME_DIR` or the system temp directory, named by a hash of the user and the canonical store path so it never pollutes the repository and users on a shared machine do not collide.
- `append_event` additionally holds a per-file exclusive lock while appending, and the projection rebuild writes `files.jsonl.tmp` first and atomically renames it over the original file.
- Reads take no locks and use plain `fs::read` (buffered file reads) rather than memory mapping, so a concurrent truncation or rebase can never cause a `SIGBUS`/undefined behavior; `MemIndex` builds `by_project` / `by_file_id` / `by_filename` indexes in memory, on which `query` and MCP's `mem_query` are both based.
- The read side tolerates per-line faults: a line that is not valid JSON is skipped rather than causing an error, so a single corrupt line does not make the store unreadable.

## Known limitations and migration notes

- **Legacy timestamp formats**: historical data may contain two legacy formats (second-precision `...Z` and nanosecond `...+00:00`). They are still readable, and time ordering is based on parsed time; newly written data uses the fixed-width UTC nanosecond `...Z` format exclusively.
- **Legacy absolute-path records**: early versions may have written a file's absolute path into `file_name`. Those records remain readable, but queries by relative path name (`query -n`, MCP `mem_query` with `filename`) will not find them. Re-running `mem add` records a relative-path identity; `mem compact -p <project>` rebuilds the projection from the event log (which also heals a missing or truncated `files.jsonl`) but does not rewrite historical `file_name` values.
- **Project names are constrained**: a project name must be one safe path component (non-empty, not `.`/`..`, no `/` or `\`, no control characters, at most 200 bytes); Windows-reserved device names (`CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9`, case-insensitive, including `con.txt`), names ending in `.`, and the Windows-invalid characters `<>:"|?*` are rejected as well, otherwise the CLI and MCP reject it with `invalid project name`.
- **Single `--fuzzy` semantics**: `--fuzzy` / MCP's `fuzzy` runs a Rust regex over the raw JSON text of event lines; it is not full-text tokenized search. Compiled regex programs are capped at 10 MiB, and an invalid regex errors out directly.
- **Git dependency**: `sync` / `resolve` require `git` to be available locally; `sync` skips the pull when the branch has no upstream, aborts on a non-conflict pull failure, and needs a push target (remote/credentials) to succeed.
- **No `--autostash`**: `sync` commits all changes before pulling and holds the store write lock, so there is nothing to stash; this avoids the hard-to-recover state where a stash pop conflicts in the middle of a rebase.
- **Concurrency scope**: writes to the same store on one machine are serialized by the store-wide lock; there is still no cross-device lock, so concurrent edits on different machines converge through Git and `mem resolve`.
